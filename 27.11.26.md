## Расчёт загрузки

Формула: `Загрузка = Запланированные часы / Доступные часы × 100%`

| Участник | Доступно | Запланировано | Загрузка | Вывод |
|----------|----------|---------------|----------|-------|
| Аналитик | 15 | 12 | **80%** | Нормальная загрузка, есть небольшой резерв |
| Frontend-разработчик | 20 | 30 | **150%** | **Перегружен** — риск задержек и ошибок |
| Backend-разработчик | 20 | 24 | **120%** | **Перегружен** — работает на пределе |
| Тестировщик | 15 | 5 | **33%** | **Недогружен** — есть свободное время |
| Дизайнер | 10 | 4 | **40%** | **Недогружен** — есть свободное время |

### Кто перегружен
- **Frontend-разработчик** — 150%, критическая перегрузка.
- **Backend-разработчик** — 120%, перегрузка.

### У кого есть свободное время
- **Тестировщик** — 33%, свободно ~10 ч/нед.
- **Дизайнер** — 40%, свободно ~6 ч/нед.
- **Аналитик** — 80%, свободно ~3 ч/нед.

### Какие задачи можно перераспределить
- **Тестировщику** — подготовка тестовых сценариев, проверка готовых модулей, регрессионное тестирование, проверка API через mock-данные.
- **Дизайнеру** — доработка макетов интерфейса, проверка вёрстки, подготовка UI-компонентов.
- **Аналитику** — согласование контракта API, документирование требований к интерфейсу.

### Какие задачи нельзя передавать без квалификации
- Написание backend-кода — только Backend-разработчик.
- Написание frontend-кода — только Frontend-разработчик.
- Проектирование БД — Backend-разработчик или аналитик с опытом.
- Тестирование кода — тестировщик (или разработчик как первичная проверка).

## Пересмотренное распределение работ

| Участник | Было, ч | Стало, ч | Загрузка | Что изменилось |
|----------|---------|----------|----------|----------------|
| Аналитик | 12 | 14 | 93% | +2 ч на согласование контракта API |
| Frontend-разработчик | 30 | 18 | 90% | −12 ч: часть задач на mock API, часть — дизайнеру |
| Backend-разработчик | 24 | 20 | 100% | −4 ч: приоритет на исправление БД, API — после |
| Тестировщик | 5 | 14 | 93% | +9 ч: тестовые сценарии, проверка модулей, mock-тесты |
| Дизайнер | 4 | 8 | 80% | +4 ч: доработка макетов и UI-компонентов |

### Ключевые решения по перераспределению

1. **Frontend переводится на mock API** — пока Backend занят исправлением БД, Frontend работает с заглушками, не простаивает.
2. **Backend сначала закрывает ошибки БД** — это блокирует API, поэтому приоритет №1.
3. **Тестировщик подключается раньше** — готовит тестовые сценарии и проверяет готовые модули через mock.
4. **Дизайнер дорабатывает UI-компоненты** — снимает часть нагрузки с Frontend.
5. **Аналитик фиксирует контракт API** — чтобы Frontend и Backend работали по одному соглашению.

## Решение руководителя проекта

### 1. Какую проблему необходимо устранить в первую очередь?
**Отсутствие согласованного контракта API и блокировка Frontend.** Backend перегружен исправлением БД, из-за чего API не готов, а Frontend простаивает. Приоритет — разблокировать Frontend через mock API и зафиксировать контракт.

### 2. Какие договорённости нужно зафиксировать?
- Контракт API (эндпоинты, форматы запросов/ответов) — письменно, в документации.
- Backend в первую очередь закрывает ошибки БД (срок — 3 дня), затем API.
- Frontend до готовности API работает на mock-данных по согласованному контракту.
- Тестировщик получает сборки по мере готовности модулей, а не в конце.
- Еженедельный статус-митинг по средам.

### 3. Кто отвечает за согласование API?
**Аналитик** — ответственный (A), **Backend-разработчик** и **Frontend-разработчик** — исполнители (R), **руководитель проекта** — информируемый (I). Контракт фиксируется в документации.

### 4. Какие задачи можно выполнять параллельно?
- Backend исправляет БД ↔ Frontend работает на mock API.
- Тестировщик готовит тестовые сценарии ↔ разработчики пишут код.
- Дизайнер дорабатывает UI-компоненты ↔ Frontend использует их.
- Аналитик согласует контракт API ↔ Backend исправляет БД.

### 5. Как контролировать дальнейшее выполнение работ?
- Ежедневный короткий стендап (15 мин): что сделано, что мешает.
- Еженедельный статус-митинг с демонстрацией прогресса.
- Доска задач (Kanban) со статусами: To Do / In Progress / Review / Done.
- Контрольные точки: контракт API утверждён, ошибки БД закрыты, mock API готов, первая сборка передана тестировщику.
- Руководитель проекта отслеживает загрузку участников еженедельно.

Проверка матрицы
У каждой задачи есть исполнитель R: да (аналитик, backend, frontend или тестировщик).

У каждой задачи ровно один A: да (руководитель, аналитик, backend, frontend или тестировщик — по одной A на строку).

Нет задач без ответственного: да.

Нет участников без обязанностей: все пять ролей задействованы.

Обязанности не противоречат друг другу: да — backend отвечает за серверную часть, frontend — за интерфейс, тестировщик — за качество, аналитик — за требования, руководитель — за организацию.

Пояснения к матрице
R — Responsible (исполнитель): непосредственно выполняет работу.

A — Accountable (ответственный): несёт итоговую ответственность за результат, ровно один на задачу.

C — Consulted (консультируемый): предоставляет экспертное мнение.

I — Informed (информируемый): получает информацию о ходе и результате.

В небольших командах допустимо совмещение R и A у одного участника (например, backend-разработчик одновременно R и A по задачам API).
